# V2 首轮：可观测信息能否指导 SQLite 的有效 checkpoint？

日期：2026-11-04（Asia/Shanghai）。目标是得到一个有用且可检验的表示、关系、策略边界或反例，并检验 V2 能否自主维护竞争解释和选择区分性实验。不要为了完成流程声称原创或系统性能提升。

## 研究起点

读取 `bootstrap/v2_scout/FOLLOWUP_SCOPE.md` 的范围和公平性要求。初测、代码与实际数字在 `bootstrap/v2_scout/BRIEF.md`、`bootstrap/v2_scout/wal_checkpoint_probe.py`、`bootstrap/v2_scout/result.json`。

相同写入量、相同 WAL 文件大小和 `busy=0` 对应了不同 checkpoint 进度。长读事务限制 checkpoint、文件保留分配空间、默认阈值和不同 checkpoint 模式的行为已经有官方解释，不能将它们重新发现后称作新 idea。

进一步的问题是：在读者释放与写入突发变化的工作负载中，只使用允许观察的公开信息，怎样识别一次 PASSIVE checkpoint 是否值得执行？能否形成相对简单周期策略的有用改进，或者找到一个明确的观测不足边界？解释与下一步实验由研究者决定；没有预定缺失变量、正确公式或正确策略。

## 可执行反馈与预算

使用项目 `.venv/bin/python` 和标准库 `sqlite3` 操作真实临时数据库。所有结果由实际 SQLite 产生；不得编造一个包含假定机制的响应函数再用它验证该机制。工作负载轨迹可以自行设计，但声明其适用范围。

每项实验阶段总预算 600 秒，实际计算宜控制在 120 秒内。规模优先几十次小实验；不要构建完整数据库压测平台。用临时目录，不操作用户现有数据库。每个角色只写自己的工作目录，不修改旧脚本。

如果比较策略，先明确观察权限、干预、所有读取/探测的成本、工作完成约束和延迟权衡。不能让候选策略知道隐藏读者释放事件，而基线只看到公开遥测。调用 checkpoint 取得信息本身可能执行工作，须计费。预先固定轨迹/随机种子和结果规则，在不同顺序的重复实验中报告结果；新轨迹形状与开发轨迹分开。计数改善、CPU/时间改善和延迟改善是不同指标。

如果研究可观测性反例，明确“相同”的信息集合、观测历史和行动时点。不能仅凭两个相同的最终数字宣称完整历史不可区分，也不能用干预后读取的结果冒充行动前特征。发现一个不充分的表示后，可以提出新的允许观察，但需要检验它是否足够，以及付出什么代价。

## 交付

形成少量有具体预测的竞争解释。每轮比较两个便宜、可执行的下一步，并选择最能改变判断的一项。允许修订解释、找到反例或放弃；保留失败预测。最终写中文结果，说明新表示/关系是否出现、哪些仅是已知机制重现、哪些还值得继续，以及最小下一项验证。

此轮没有与 V1 或单 agent 进行相同预算对照，因此不能宣称组织结构提升了发现性能。
